## 29. 后期内容补齐：STRATZ 默认只给 35 分钟（2026-10-26）

玩家反馈（原话）：「现在的内容，到了后期以后几乎都没有了」；要求同分段每分钟数据「至少存到 50 分钟，如果一局没有 50 分钟就按它当前最长时间来算」，并且「需要搞明白」。

**查明的原因**：STRATZ `heroStats.stats` **不写 `maxTime` 时默认只算到 35 分钟**（文档没写，2026-10-26 实测），影响三处：
| 哪里 | 以前 | 问题 |
|---|---|---|
| `coach.fetch_bench` 每分钟正补 / 经济（`groupByTime`） | 只有 0~35 分钟 | 35 分钟后局内提醒没有节奏对比 |
| 同上的「总局数」、`brief.fetch_hero` 的「总局数」（不分时间的 `stats`） | 其实是**打到 35 分钟还没结束的局数**（约 2/3） | 装备比例的分母偏小（以前靠「买鞋最多的局数」兜住了，第 25 节注释里「stats 2513 局、动力鞋 3533 局」就是这个原因）；起手装比例偏大 |
| `data.fetch_positions` 分位置胜率（推荐排名用） | **只算 35 分钟以上的局** | 后期英雄胜率偏高、前期英雄偏低：172 个「英雄 × 位置」（≥2000 局）差值中位 1.35 个百分点，最多 ±6（虚空假面一号位 53.0 → 实际 47.1，美杜莎 55.1 → 49.2，幻影长矛手 57.8 → 52.8；兽王三号位 40.8 → 47.6，小小一号位 41.7 → 45.9） |

实测：`maxTime` 写多大都只给到 **75 分钟**；不分时间的 `stats` 给的是「最后一分钟（maxTime）那一桶」的局数；`maxTime: 0` = 全部对局。
第 t 分钟的平均值是「打到第 t 分钟还没结束的局」的平均，正好和「你这局也打到了第 t 分钟」可比。

**改了**：
- `coach.fetch_bench`（`BENCH_VERSION` 5）：`maxTime: 90`（实际到 75），每分钟要 ≥100 局（`PER_MIN_MIN_MATCHES`），冷门英雄就到它数据够的最后一分钟（敌法一号位到 72、炼金中单到 47）；总局数改用第 0 分钟的局数。
  装备核心 / 常见的判断基本没变（真正总局数 ≈ 买鞋最多的局数）。
- `brief.fetch_hero` 总局数加 `maxTime: 0`，缓存文件名加 `_v2`。
- `data.fetch_positions` 先改成 `maxTime: 0`（全部局；后来玩家定为 ≥30 分钟，见下），分位置数据已重拉。回测（同一批 1523 场样本外对局）：区分度 全部 0.0638 → 0.0673、前 4 手 0.0459 → 0.0496、后 4 手 0.0736 → 0.0765，阵容预测对数损失 0.6694 → 0.6683，都略好（在噪声内）。
  **副作用**：拉席克一号位在 `K_PICKS = 10000` 下又排回一号位第一（53.5，幽鬼 52.8）。原因：一号位拉席克的局多半是速推，
  35 分钟内结束的那部分赢 72%（286 / 396），以前被丢掉了，只剩长局 493 局 55.0%（和拉席克各位置平均 55.5% 差不多，没有加成）；
  现在 889 局 62.7%，比拉席克平均高 8 个百分点，收缩前 59.6%，按局数（≈5500）收缩系数 0.36 后 53.5%。
  单一位置英雄（幽鬼、幻影长矛手）几乎不受影响：位置加成是「这个位置 - 这个英雄所有位置」，两边同样只算长局，偏差抵消了。
  重扫 K_PICKS：15000 时和幽鬼 / 主宰并列，20000 时排第四（区分度 0.0643）。
  又试了「只算打到第 N 分钟的局」（同一批回测，K_PICKS 10000）：
  | 只算 | 每周局数 | 拉席克一号位 | 区分度（全部 / 前 4 手 / 后 4 手） | 一号位第一 |
  |---|---|---|---|---|
  | 全部 | 13.3 万 | 891 局 62.7% | 0.0673 / 0.0497 / 0.0765 | 拉席克 53.5 |
  | ≥25 分钟 | 12.9 万 | 839 局 61.4% | 0.0676 / 0.0507 / 0.0762 | 拉席克 53.1 |
  | **≥30 分钟（采用）** | 11.6 万 | 717 局 58.7% | 0.0666 / 0.0483 / 0.0757 | 幽鬼 52.8（拉席克 52.2 第四） |
  | ≥35 分钟（以前不知情时） | 8.8 万 | 498 局 54.6% | 0.0651 / 0.0483 / 0.0745 | 幽鬼 52.8 |
  25 分钟前结束的只有约 3%，去掉它们压不住拉席克（它的速推局多在 25~35 分钟结束）。
  **玩家定：只算 ≥30 分钟的局（`data.POSITION_MIN_MINUTES = 30`），K_PICKS 不动（10000）**。分位置数据已按这个重拉。
  代价：比「全部局」略偏后期英雄（区分度差 0.0007，在噪声内）。克制 / 配合（OpenDota）和英雄整体强度不受影响，仍是全部 ≥15 分钟的局。
  第 2.1 节的回测数字都是旧数据跑的。

**后期补的内容**（玩家 2026-10-26 选了「后期页加数据」「买活」「格子满了卖东西」，并说出装「还是应该依据对方英雄来判断」）：
- 本局要点「后期」那页加「后期出装」小节（`itembuild.late_lines`）：30 分钟后的出装顺序 + 针对装理由；30 分钟前的针对装再提一句「到后期还没有先补」；
  一行规矩「格子满了先卖身上最便宜的那件；30 分钟后买大件前留够买活钱」。中期那页的「出装」只放 30 分钟前的。
  有出装数据时后期那页就有内容，没开 AI 也会在 30:00 弹。
- 「下一件」（死亡 / 时间点卡片）：身上 6 格满了加「格子满了，先卖 X（N 金，身上最便宜）」（`itembuild.sell_pick`：按买价最低；身上有下一件的零件就不提；
  吃掉 / 用掉的消耗品（树枝除外）和不朽之守护不算——实现假设）；30 分钟后钱够了但买完不够买活，加「但买完只剩 N，不够买活（M）」。
  买活价来自 GSI `hero.buyback_cost / buyback_cooldown`（2026-10-26 实战推送里有；`buyback_cooldown` 是冷却结束的 `map.game_time`，不是还剩几秒，见 `gsi.buyback_left`；没有这个字段就不提）。
- 肉山计时：玩家说无所谓，没做。

**验证**：单元测试（卖哪件、买活、按阶段拆出装、GSI 6 格 / 买活字段）；`brief-sim 9055590694` 看了中期 / 后期两节；`coach-sim 9054096051`（55 分钟）跑通；卓尔一号位每分钟数据到 67 分钟。
**没在真实对局里看过**。

**还没做 / 要玩家定**：
- 「依据对方英雄判断出装」：新加一类针对装「幻象」（`coach.COUNTERS` 的 `illusion`）：对面有能自己造一群幻象的英雄
  （按技能原文匹配，结果正好是幻影长矛手、娜迦海妖、混沌骑士、恐怖利刃；幽鬼如影随形「无法控制」、暗影恶魔造的是别人的幻象，不算），
  从雷神之锤 / 狂战斧 / 辉耀 / 希瓦的守护里挑你这个英雄同分段出得最多的（≥3% 的局买才算）。抽查对面有幻影长矛手：敌法 / 主宰 → 狂战斧，
  冥魂大帝 → 辉耀，风暴之灵 → 雷神之锤，斧王三号位 → 希瓦，斯温 / 宙斯 / 莱恩 → 不推。**装备选哪几件是实现假设，要实战调**。

## 83. 版本更新以后的胜率只用更新以后的数据（2026-11-20）

玩家 2026-11-19 定：「版本更新以后的胜率要拿更新以后的数据」。以前 `update` 克制 / 配合拉最近 `days` 天（14），7.42 上线后一天多那份里九成多还是 7.41f 的局；STRATZ 分位置 / 对线不写 `week` 给的是上一个整周，也全是旧版本。

**上线时间**（`stats.patch_start`）：OpenDota `constants/patch`（只有大版本，时间是真正上线的时刻，7.42 = 11-18 21:28 UTC，和 STRATZ 分小时出场率翻倍对得上）和 Valve datafeed 更新日志（有字母小版本，但时间只写到当天 07:00 / 08:00 UTC，7.42 比真上线早 13 小时）取晚的。字母小版本只有 Valve 那个时间，会多算进当天上线前几个小时的局，接受。两个都拉不到就不切，照旧按天数。

**怎么切**：
- 克制 / 配合（`fetch_stats`）：上线不到 `days` 天时，先用 explorer 查上线后第一局的 `match_id`（约 2 秒），从那开始，每块 SQL 再加 `start_time >= 上线时间` 精确切。文件里记 `since` / `patch`，`suggest` 抬头显示「7.42 上线以来 N 局」。
- STRATZ 分位置 / 对线（`stratz_week`）：STRATZ 的周从 1970-01-01（星期四）起每 7 天，`week` 传那周开始的 unix 秒（实测：不写给上一个整周，写了给那周、没过完的当周也给）。上一个整周全在新版本里 → 照旧；当周是上线以后才开始的 → 取当周（7.42 是星期三晚上上的，正好赶上）；版本是这周中间上的 → 分位置改用 `winDay`（晚一天才有）+ `winHour`（只有最近约 30 小时）按位置凑上线以后的（这两个接口不能按时长筛，`min_minutes` 记 0），对线（`laneOutcome` 只能按周）返回 `None`，`update` 删掉旧的对线文件、选人卡片先不显示对线，等下周四。
- 没填 STRATZ token 时 OpenDota 分路凑的分位置数据没法按时间切，没动。

**取舍**：上线头几天局数少（7.42 上线 29 小时，超凡以上 5.8 万局，以前 14 天 84 万局），克制 / 配合 / 分位置都靠引擎原来的收缩往「按自身强度的期望」拉，克制关系比以前弱、更多看英雄自身强度。这是玩家要的——旧版本的克制数据对重做英雄是错的。满 14 天后自动回到「最近 14 天」。

顺手修：7.42 新装备（stone_of_recall 等 4 件）CDN 上还没图，`fetch_item_icons` 遇 404 直接崩、整个 `update` 中断；现在跳过并在日志里列出来，下次 update 再试。

**验证**：`tests/test_patch_cut.py`（上线时间取哪个来源、start_time 切、挑哪一周、这周中间上的按天 + 按小时凑且不重复算、对线返回 None）；真跑 `update`（7.42：克制 / 配合 57617 局从 match_id 9095964276 起，分位置 / 对线取 week 1795046400）；`suggest` 抬头显示「7.42 上线以来」，推荐结果看着正常。「这周中间上」那条路径用假的上线时间对真 STRATZ 跑过一次（127 个英雄都有数），真实情况要等下一个字母版本。

**启动时保证是当前版本**（同节补，`app/start.py` 的 `full_update_reason`）：以前启动只看克制数据文件满没满 3 天，新版本上线后最多还要用 3 天旧版本的数据。现在启动时再联网问一下当前版本（`patch_start`，两个请求），克制数据的 `fetched_at` 早于上线时间就马上全量更新；文件里有 `since`（上线不满 `days` 天，只统计了上线以后的局，局数涨得快）就 24 小时一更。问不到版本（没网）照旧用旧数据。`tests/test_patch_cut.py` 的 `StartupUpdateTest`。

**还没切的**：局内出装竖条用的 `knowledge/item_vs.json`（第 80 节）是 7.41f 的 17.3 万局整理出来的购买比例（不是胜率），要等 7.42 局数够了再按第 79 节的脚本重算；个人数据（你打过几局、胜率）是熟练度，不按版本切。

## 86. 字母小版本不切数据，知识库跟到字母小版本（2026-11-25）

7.42a 11-24 上线（40 个英雄 + 斯嘉蒂之眼等小改）。按第 83 节的做法它算新版本：下次启动会全量更新，克制 / 配合 / 分位置只剩上线后 1 天的局。玩家 2026-11-25 定：**字母小版本不切数据**，胜率从大版本（7.42）上线一直算；**知识库要是最新版本**，各台电脑都要。

**改了什么**：
- `stats.patch_start` 只认大版本：OpenDota 那边本来就是大版本；Valve 更新日志取最新一项所属的大版本（`stats.major`：`7.42a` → `7.42`），时间取这个大版本的第一项（不带字母的 7.42）。两边照旧取晚的，所以 7.42 还是 11-18 21:28 UTC。OpenDota 还没收录新大版本时，Valve 的 7.43 比 OpenDota 的 7.42 新，照样马上切。`full_update_reason` 不动：字母小版本不会让它全量更新，也不会让 suggest 抬头变成「7.42a 上线以来」。
- 知识库单独跟版本（`app/start.py` 的 `ensure_kb`）：以前知识库只在全量 `update` 里跟着更新，字母小版本不再触发全量更新后，最多要等 3 天。现在每次启动时，不需要全量更新就看一眼 Valve 当前版本（`kb.current_patch`，一个请求），本机 `kb.local_patch()` 对不上就重拉知识库，连带大招神杖 / 魔晶写法（`cd_ops`，按知识库版本存）和对面大招图标（`update.fetch_icons`）。失败（dota2.com 断连接）只打一行，用旧的照样启动。
- 其他电脑：游戏电脑（源码版 `git pull`）、朋友的打包版（更新助手时 `data/` 只补本地没有的，自带的 kb.json 不会被换）都靠启动时这一步跟上；`packaging/build.py` 的 `prefetch` 打包前也先 `kb.update`，打进包的知识库不比 Valve 旧。AI 打法缓存的 key 里有资料原文（含版本号和数值），知识库一换自动失效，不用另外处理。
- **没管的**：助手开着的时候出了新版本，`Live` 里已经加载的知识库不会换，要重开一次（Dota 本身更新也要重开）。

**验证**：`tests/test_patch_cut.py`（字母小版本还按 7.42 真上线时间、OpenDota 拉不到时取 Valve 7.42 第一项、新大版本 OpenDota 没收录时照样切、`EnsureKbTest` 同版本不拉 / 小版本重拉 + 补图标 / 本机没有知识库）；真跑 `ensure_kb`：本机 7.42 → 7.42a（127 个英雄、261 件物品，大招神杖 / 魔晶 14/14，约 2 分钟；第一次 dota2.com 连续断连接 6 次失败，重跑成功），再跑返回 False；`kb item 斯嘉蒂之眼` 是 +32 全属性，幻影刺客窒碍短匕 25/40/55/70%，死神镰刀冷却 95；真接口 `patch_start` = ('7.42', 11-18 21:28 UTC)；`suggest` 抬头还是「7.42 上线以来 57617 局」；`build.prefetch()` 输出「知识库已是最新版本 7.42a」。
