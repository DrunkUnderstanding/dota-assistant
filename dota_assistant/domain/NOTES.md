## 16. 选人时的「为什么选 / 选了怎么打」（2026-10-22，`explain.py` + `live.explain_pick`）

玩家反馈（原话）：「现在选人的时候没有说明为什么这么选人，为什么这么选，选了这个要怎么针对」。
玩家选了混合做法：机制说明秒出、不用大模型；点某个推荐英雄再让 AI 写打法。

**1. 推荐卡片下的机制说明（`explain.matchups`，不影响排名）**：推荐英雄 × 已选敌方英雄，按知识库标签对照，每条带两边的官方原句（悬停可看）。
| 我方 | 对面 | 说法示例 |
|---|---|---|
| 克敌机先 / 无视闪避 | 提供闪避 | ✓ 射手天赋无视闪避，风行者的风行闪避对你无效 |
| 反隐 / 显形 | 隐身（原文写「不会被反隐」的除外） | ✓ 狂风能显形，赏金猎人的暗影步隐身藏不住 |
| 施加破坏 | 怕破坏 | ✓ 末日（神杖）能施加破坏，敌法师的法术反制被破坏后失效 |
| 无视技能免疫 | 提供技能免疫 | ✓ … 开剑刃风暴也躲不掉 |
| 提供技能免疫 | 控制且官方 immunity 字段「不无视免疫」 | ✓ 剑刃风暴有技能免疫，能躲风行者的束缚击 |
| 反过来对面压我（前四组对调） | | ✗ 幻影刺客的刀阵旋风能施加破坏，你的剑心犹在被破坏后失效 |

每个敌人最多一条「克」，每个推荐最多 2 条克 + 1 条怕。来自神杖 / 魔晶的标注出来。
- 覆盖面有限：随机 40 组阵容只有 15 条说明，大部分英雄对位没有这种硬机制，那时就只有统计理由（克 X +2.1%）。
- 试过「强驱散 → 能解对面眩晕」，抽查出来大多没意义（例如解巨力重击），删了。
- 顺手收紧了 `kb.TAGS` 的「反隐 / 显形」：以前「攻击后自己显形」「不会使斯拉克显形」「迷雾中显形」都会命中。

**2. 点推荐英雄 →「如果选 X」卡片（`Live.explain_pick`）**：按当前局面、当作已经选了 X，调同一套 `brief.build`（数据页）+ `gameplan.generate`（AI 打法页），
做好 AI 页自动翻过去；叠加层和控制面板预览都能点（叠加层固定时，推荐卡片和翻页标签也算可点区域，其余地方照样点穿）。
标签或 F6 翻页，× / F8 回到推荐（不收起叠加层）；阵容变了标题会提示「再点一次更新」；选完人进策略时间后由真的本局要点接替。
实测（2026-10-22，露娜一号位 vs 风行者 / 幻刺 / 斯拉克）：AI 页 37 秒，折合 API $0.13；STRATZ 当时 503，数据页只有对线对手猜测和「对面要防」。

**未验证**：叠加层点击、卡片排版没在真机 Electron 里看过（开发环境里 Electron 起不来）；AI 打法的局限同 15.1 节。
游戏电脑原来没装 Claude Code 命令行，AI 打法页之前一直是空的；2026-10-22 已用 npm 全局安装（2.1.308）并确认已登录。

## 22. 对面分路 + 对线打法（2026-10-23，`lanes.py`）

玩家需求（原话）：「根据对手阵容判断对方分路，然后根据分路来推荐对线的打法」。
玩家选的做法：**选人时和策略时间都要**；建议**规则 + 数据秒出、AI 补充**；**三路都显示，重点是我这路**。

**猜分路**（`lanes.guess`）：沿用本局要点原来的猜法（每个英雄在本分段打各位置的局数比例相乘、五人位置不重复，STRATZ `positions_*.json`），
多算了每人的「把握」：所有分法按可能性加权，他在这个位置的分法占多少。把握 < 60% 标「?」。
天梯一 + 五号位走自家优势路、三 + 四号位走劣势路；天辉优势路是下路，夜魇是上路（不知道阵营时写「对面优势路 / 劣势路」）。
同路队友：选人界面 OCR 认出的队友位置（`Live.team_roles`，第 20 节）优先，认不出就同样按比例猜（我的位置先占掉）。

**回测**（`python -m dota_assistant lanes-test`，和 `backtest` 同一批 3000 场超凡～冠绝天梯全英雄选择，统计截止之后的对局；
位置数据是 STRATZ 最近一周，和这批对局时间有重叠，数字可能略偏乐观）：
| 项 | 结果 |
|---|---|
| 五人选完，单人位置猜对 | 79.8%；走哪条路猜对 81.6%（大部分错是核心 / 辅助跨路，不是 3、4 号位互换） |
| 把握分档 → 实际猜对 | 20~40%：34.9%；40~60%：52.4%；60~80%：69.4%；80~100%：93.7%（把握基本是准的） |
| 对面只选了 k 个时，已选的人猜对 | k=1 61.9%、2 63.8%、3 69.4%、4 74.2%、5 79.8% |
| 我这路对面是哪几个人，完全猜对 | 中单 81.4%、三 / 四号位 68.0%、一 / 五号位 62.3% |

试过（没上线）：加「这是本队第几手」的先验（天梯里前两手 84% 是四 / 五号位，最后一手 48% 是中单），一半对局估先验、一半验证，单人猜对 79.9% → 81.4%。
没做是因为实时版不知道对面的选人顺序（选人阶段可能看不到对面已选，见第 6 节），以后能拿到顺序再加。

**对线提示**（`lanes.tips`，只看对线期技能：非大招、非神杖 / 魔晶给的；只看说明正文）：按顺序最多 4 条
1. 对面同路的控制（眩晕 / 沉默 / 缠绕 / 妖术 / 缴械）：两个控制 →「都在时别压到线前，交了一个再换血」；一个 →「小心 X（冷却 …），交了以后是你换血 / 补刀的窗口」
2. 持续施法（官方 `behavior` 字段的持续施法位，比关键词可靠）：对面的 → 用你 / 同路队友的眩晕 / 妖术 / 沉默打断（缠绕不打断）；你自己的 → 会被对面打断。
   施法时躲进别的位面的（帕克相位转移、力丸绝杀秘技）不算
3. 射程（官方数据 `attack_range`）：近战对远程、远程对近战、远程射程差 ≥100

## 24. 剩余位置推荐（2026-10-24，`advisor.team_slots`）

玩家需求（原话）：「帮我加一个，剩余位置推荐选择功能」。

**理解成（实现假设，玩家没细说）**：我还没选英雄、队友已经选了人时，告诉我我方还剩哪几个位置、每个剩余位置我该选谁，帮我挑打哪个位置。

- **队友占了哪几个位置**：`lanes.guess`（和对面分路同一套猜法）。选人界面 OCR 认出的队友位置（第 20 节 `Draft.ally_pos`）直接用，其余按「本分段打各位置的局数比例相乘、五人不重复」猜；
  **不先替我占位**（对面分路那里是先把我的位置占掉再猜队友），所以队友可能被猜到我当前的位置上——这正是要提醒的情况。没有 STRATZ 分位置数据时只用 OCR 认出的。
- **剩余位置推荐**：每个空位置跑一遍 `engine.suggest`（同一套打分：英雄池 / 个人战绩 / 位置筛选都照常），按 `split_targeted` 分「推荐 3 + 针对这局 3」（`TEAM_TOP` / `TEAM_TARGETED`，见下面 24.1；原来是前 2 个）；
  当前位置直接复用已经算好的结果。五个位置一起算约 15~50 ms（开发机，克制缓存冷 / 热）。
- **推荐打哪个位置**：空位置里第一推荐的综合分最高的（`Advice.best_open()`）。综合分含熟练度和个人战绩，所以常玩的位置天然占优。
- **什么时候有**：至少一个队友选了人，或者我已经选好英雄；**一直显示到进游戏**（GSI 进入出门 / 比赛阶段，`Live.draft_view` 把它去掉）。
- **我选好英雄以后**（2026-10-25 玩家要求，原话：「位置推荐功能可以不用在我选完人以后关闭掉，等待到进入游戏再切换」）：
  我占当前位置（这格显示我的英雄、标「你」），其余队友按常打位置猜时不再占我的位置；空位置的推荐改成**给队友的**：
  `engine.suggest` 把我也算进我方（算配合），**不带我的英雄池 / 个人战绩**；不再标「推荐打哪个位置」，空位置也不能点了。
  命令行写成「剩余位置：（给队友）… （已占：三号位 你 冥魂大帝、…）」。策略时间本局要点会照常盖上来（第 15 节），号角后卡片收起时选人卡片里已经没有这块。
- **显示**：叠加层 / 预览左栏，阵容下面、对面分路上面一块「剩余位置」，五行：队友占了的灰显 + 队友头像（猜的带「?」）；
  空的显示两个推荐头像 + 胜率；推荐的位置描金边标「推荐」，当前位置标「当前」；队友占了当前位置时标红「队友占了你的位置」。
  **点空位置 = 切到那个位置**（网页动作 `set position`，和控制面板位置按钮同一条路，这局不再被自动认位置改回去）。
- 命令行 `suggest` 多一行「剩余位置：…（队友占了：…）→ 推荐打 X」。
- 验证：`tests/test_webui.py` 的 `TeamSlotsTest`（空位置 + 推荐位置、OCR 位置优先且占了我的位置、没队友时不出、我选好后给队友推荐）、
  `CoachLiveTest.test_team_kept_after_pick_until_game`（选人阶段选好后还在，出门阶段去掉）；
  `suggest --ally 敌法师,冰女 --enemy PA,莱恩 --pos 1`：敌法师猜一号位、水晶室女五号位 → 剩中单 / 三 / 四，推荐打三号位（冥魂大帝 59.2%）；
  无头 Chrome 截图看过 420 宽和 720 宽（两栏）排版，以及选好冥魂大帝三号位后的样子。
- **已知局限**：对面分路那块仍然按「我打当前位置」先占位再猜队友，所以队友被猜到我当前位置时，两块显示的队友位置会不一致，切到推荐位置后就一致了。

### 24.1 每个空位置 3 + 3、展开收起（2026-10-26）

玩家要求（原话）：「剩余位置的选择应该是展开收起的，然后选择应该是3+3」。

  我选好以后给队友的推荐也是 3 + 3。命令行一行写成「中单 A 54.0% / B / C ｜针对 D / E / F」。
- **展开收起**：每个空位置默认只露第一推荐 + 行尾「▾ 3+3」按钮；点按钮展开成两排（「推荐」「针对」各 3 个头像 + 胜率），再点「▴ 收起」。

## 26. 推荐分两组：推荐 + 针对这局（2026-10-26，`advisor.split_targeted`）

> 2026-11-02 起给我的推荐改成四小组（第 49 节）；这里的做法现在只用在剩余位置给队友的「推荐 + 针对」。

玩家反馈（原话）：「每一局推荐的英雄都有些趋同……也不是完全相似，就是近似」→ 选了「3 + 3」。

**原因**（随机抽几百个局面实测，超凡～冠绝 14 天数据）：每个位置自身强度第 1 名比第 20 名高 3~5 个百分点，
单个敌人的克制中位数才约 1 个百分点、正负还会抵消；个人数据、对线加权、反制风险又都关着。结果每局前 5 里平均约 2 个来自同一批 6 个「常驻」
（一号位幻影长矛手 / 幽鬼 / 拉席克 / 冥魂大帝 / 米波 / 主宰，三号位谜团 65%，四号位赏金猎人 68%）。
冷门降权（K_PICKS）不是原因：关掉它反而更集中（一号位两局前 5 重合 1.2 → 2.3 个）。

**做法**：「推荐」= 综合分前 `top`（3）个；「针对这局」= 剩下的里按 `Suggestion.situational`（综合分 − 自身强度 = 克制 + 配合）排前 `top_other`（3）个，
要求综合胜率 ≥ 50%（不然会挑出自身 −6% 的小小，克一个人也救不回来）。没人选时只有一组，共 `top + top_other` 个。
播报只念「推荐」的前两名。理由里单项克制 / 配合都不显著、但合计 ≥ 1 个百分点时写「克制 + 配合合计 +x%」，不再写「版本强势」。
玩家本机 config.toml 的 `top_other` 改成了 3。

**顺手修的**：今天 11:28 跑过一次 `update`，STRATZ 分位置接口返回了空表，把 `data/positions_r7-8.json` 覆盖成空的，
推荐退回按定位标签筛位置（赏金猎人、幽鬼进了中单）。`data.update` 现在拿到空表就保留旧文件；当时已重新拉取（127 个英雄）。
今天打的包里带的是 10-20 的分位置数据，不受影响。

**没改的**：对线对手加权（`W_LANE`）、被反制风险（`W_RISK`）仍为 0，见第 2.1 节回测；「易被反制」只是理由里的提示。
**下一步**：实战看「针对这局」的英雄是不是真能选、是不是太偏门（圣堂刺客、矮人直升机一号位这类）。

## 43. 推荐按熟练度分组 + 每个推荐的胜率怎么来的（2026-10-30，`advisor.split_targeted` + `Suggestion.breakdown`）

**复盘 10-29 晚 6 局（1 胜 5 负，玩家和同一位朋友双排）**：拿 OpenDota 整局数据按选人顺序重算每一手当时的推荐，对上选的人这个英雄的生涯局数：

6 局样本说明不了统计问题，只是现象和机制对得上。

**A. 「推荐」只放会玩的**（玩家选的方案 A + C）：

**胜率怎么来的**（`Suggestion.breakdown` / `calc_text`，`advisor.calc_view`）：每张卡片多一行「自身 52.4（整体 51.0 · 一号位 +2.0 · 局数少 −0.6）＋克制 6.2 ＋配合 3.1 ＝ 61.7」，

### 43.1 打分改了两处：冷门打折按选取率、配合不再打七折（2026-10-30，回测定的）

玩家看了算法行后问：「米波、维萨吉总出现在推荐榜上……基础胜率是不是太高了」「没必要硬拉，就再乘一个选取场次或者选取率的系数就好了」「克制是 2.1，那么和配合的 2.1 应该是相等」，并同意「回测不支持结论，允许调整」。
- **原来的毛病**：自身强度按「这个英雄打这个位置的局数」`n / (n + 10000)` 往 50% 拉，两个方向都拉（树精四号位 45.8% 被抬到 49%），对冷门的又只砍一半（米波中单 55.9% → 53.0%），系数还随统计天数变；配合最后再乘 0.7，算法里已经按样本收缩过，等于打了两次折，文档里也没理由。
- **回测**（`%TEMP%` 下的临时脚本，走 `backtest.fetch_matches`：统计截止之后的 1738 场样本外对局；同一批对局配对比较，差值 95% 区间按场次自助法 300 次）：

| 自身强度 | 配合 0.7 | 配合 1.0 | 配合 0.5 |
|---|---|---|---|
| 原来（局数系数） | 0.0603 | 0.0615（+0.0012，−0.0007~+0.0032） | 0.0594 |
| 不打折 | 0.0630 | 0.0626 | 0.0626 |
| 选取率门槛 3%，只压高于 50% | 0.0636 | 0.0640（+0.0038，+0.0006~+0.0070） | 0.0636 |
| 选取率门槛 5%，只压高于 50% | 0.0640（+0.0037，+0.0005~+0.0070） | **0.0640（+0.0037，+0.0006~+0.0071）** | 0.0638 |

  （数字是选人区分度 = 实际选的排名 ↔ 胜负的相关系数；前 4 手 0.0340 → 0.0414；阵容对数损失 0.6708 → 0.6704。改善不大，区间刚好不过 0，比了 12 种组合，有一点多重比较的运气成分。）
- **采用**：`PICK_RATE_FULL = 0.05`（这个位置选取率不到 5% 的，高出 50% 的部分乘 选取率 / 5%；低于 50% 的不动；选取率 = 局数 / 统计期总局数，不随天数变），`W_SYN = 1.0`（1:1，回测没有可测的差别）。
  `K_PICKS` 删了（`docs/refactor/moves.json` 那条加了 `removed`，`test_moves` 认这个字段跳过）。算法行里「局数少」改叫「冷门打折」。米波中单 55.9% → 51.4%，空阵容中单推荐变成祈求者 / 龙骑士 / 撼地者 / 力丸…；主流英雄（选取率 ≥ 5%）自身强度不再被拉。

**「针对这局」的显示**：一度把这组卡片主数字改成「克制+配合 +9.9」、算法行从克制写起（玩家：「我当前看到的数值还是会计算它这个英雄的整体胜率」）；看过后玩家改主意（原话：「下面的这个还是和上面的这个一样显示胜率吧……计算方式既然都是一样的，那就没必要……显示得不同了，只要现在把相对应的计算数据放上去就行了」），现在两组卡片显示完全一样：右上角总胜率 + 同一行算法「自身（整体 · 位置 · 冷门打折）＋克制＋配合＝总胜率」。「针对这局」仍按克制 + 配合挑和排（按显示的百分点 `situational_pct`，自身只用来筛掉总胜率不到 50% 的），所以组内总胜率不一定从高到低。
之后玩家又要「克制分类里把克制值放上去，一眼看得到」「克制值和配合值需要分开放，不能用同一个颜色」：「针对这局」卡片右上角胜率前面加两个标签「克制 +7.9」（绿）「配合 +2.0」（蓝，负数红），数值就是算法行里的克制 / 配合两步；命令行写成「天穹守望者  62.3%（克制 +7.9 配合 +2.0）」。「推荐」卡片不加。

## 45. 胜率是不是「对位直接相加」+ 叠加层顶上的「阵容」胜率（2026-10-30，`Engine.draft_rest` + `advisor.draft_rate` + `backtest.additivity`）

玩家问：「现在的这个胜率计算直接计算加和是不是不太好，感觉这个各对位的胜率加和计算并不能够反应真实胜率」。看完分析后要求两件都做：A 卡片上加「选它后我方阵容胜率」，B 扩大回测样本看克制叠多了是不是有上限。

**先说清楚现在怎么算**：不是把对位胜率相加。克制 = 对位实际胜率 −「按双方自身强度该有的胜率」，只算多出来的部分，再按局数收缩；所有项在 logit 里相加，最后换回胜率（第 43 节的算法行）。

**B：逐项相加有没有算多（`backtest` 报告第五节，5950 场样本外，统计截止 match_id 9066632453 之后）**：拿最终阵容的三项（天辉 − 夜魇）拟合各自的系数，1 = 直接相加刚好，< 1 = 5 个对位 / 10 对配合各自统计、相加时重复算了。

| 项 | 系数（95% 区间） |
|---|---|
| 三项合计 | 0.92 ±0.12 |
| 强度 / 克制 / 配合 | 0.98 ±0.17 / 0.91 ±0.19 / 0.75 ±0.35 |
| 天辉截距（各项系数固定 1） | +0.133 ±0.052 logit ≈ +3.3 个百分点 |

按克制合计分档，逐项相加的预测和实际都在区间内，克制最大的两档（+0.4~+0.6：预测 64.9% 实际 62.8% ±5.1；+0.6 以上：70.0% 对 70.5% ±8.7）也没有「叠多了到顶」。
第一次只有 1738 场时最高那档是 64.9% 对 57.5%（153 场），换成大样本后不成立，是噪声。**结论：不改权重、不加封顶**。配合 0.75 区间含 1，`W_SYN = 1.0` 是玩家定的，没动；以后样本更多、区间不含 1 了再说。
阵容预测：准确率 58.4%，对数损失 0.6715（瞎猜 0.6931）。只看阵容本来就只能预测到 60% 上下，卡片上 60% 以上的数实战要打折看。

**A：卡片上的胜率不是全队胜率**：它只算候选自己（自身 + 对每个已选敌人的克制 + 和每个已选队友的配合），其余 9 个人当平均水平。队友被克、对面配合好都没算——玩家觉得「不像真实胜率」主要是这个。
- **先做成每张卡片一行**「全队 61.3 ＝这手 57.0 ＋队友 4.0 －对面 1.9 ＋天辉 2.2」。玩家在 Electron 演示里看了说（原话）：「要不就不显示了，只放一个结果放在上方就好，现在这个显示出来会导致我的整个游戏的排版有点拥挤，我看到这个全队胜率似乎就是一个针对我选择的这个英雄增加的胜率」。
  确实：「队友 / 对面 / 阵营」三项对同一手的每个候选都一样，每张卡片重复一遍没有信息量。
- **现在**：叠加层标题栏右边（「选人助手」前面）一个「阵容 59.4%」，悬停写怎么算的；命令行 `suggest` 标题下面一行「阵容胜率 54.8%（已选的英雄 + 天辉，你这手按平均算）」。卡片上的「全队」行去掉了。
- 算法：已选的我方（队友位置用选人界面认出的，其余和分路同一个猜法 `lanes.guess`，猜不出用整体强度；**我选好后算上我**，按当前位置）各人自身强度 + 每人对每个已选敌人的克制 + 两两配合，减去对面已选各人自身强度 + 两两配合，再加阵营（天辉 +`RADIANT_EDGE` 0.13 = 上面拟合的截距，夜魇 −，不知道阵营 0）。没选的人当平均水平，所以前几手会贴近 50% + 阵营。
- 和回测预测整局胜负是同一个式子（`backtest.predict_drafts`），上面的系数就是在验证它。不影响排名。还没人选时不显示。视图顶层多 `draft_rate: {winrate, note}`（没人选时 null）。

**验证**：`tests/test_familiar.py` 的 `DraftRateTest`（和整局式子相等、天辉 / 夜魇 / 不知道阵营、选好后算上我、没人选不显示、卡片上没有「全队」、排名不变）；真实数据里 `advantage(a, b) = −advantage(b, a)`（最大误差 1e-15），所以不用像回测那样再对称化；
全部单测、ruff、编译、`node --check`；`suggest` 冒烟；Electron 演示（`demo --step 10`）里玩家看过每卡一行的版本，改完重开演示，用浏览器开同一个服务的叠加层页面截了标题栏：「一号位 天辉 …… 阵容 59.4% 选人助手」，没有挤。
`check_isolation` 跑的时候演示正在写 `shots/deaths/`、`logs/`，报的改动是演示写的，不是单测。
**没验证**：没实战；行为快照这台机器没有（cli 快照多「阵容胜率」行、视图多 `draft_rate` 字段，有快照的机器上跑会有这些差异）。

## 73. 克制等级 S~F + 配合权重改 0.5（2026-11-09，`engine.GRADE_CUTS` / `Suggestion.counter_grade` / `W_SYN`）

**起因**：玩家看了同行 gg-go-next（开源 Dota 叠加层，STRATZ 冠绝 / 超凡数据）的选人打分「克制合计 + 0.5 × 配合合计」和 S~F 等级，觉得有意思，要「1 试试（等级）、2 试试 0.5」。

**克制等级**：
- gg-go-next 按「平均每个敌人的克制」分档（≥2 S、≥1 A…），线是按没收缩的胜率差定的。我们的克制收缩过，照搬几乎拿不到 S；而且 k 个对位的平均随人数变窄（实查：1 个敌人第 90 百分位 +1.87，5 个时平均只有 +0.85），只看平均会「敌人越多越难拿 S」。
- 改成按「克制合计 ÷ √敌人数」分档，不管几个敌人都和单个对位同一个分布。档位线 = 全部约 1.6 万对对位的第 90 / 75 / 50 / 25 / 10 百分位（+1.9 / +1.0 / 0 / −1.0 / −1.9）：S 前 10%、A 10~25%、B 25~50%、C 50~75%、D 75~90%、F 最后 10%。只看克制，不含配合和自身强度。
- 显示：卡片胜率前面两个方块「克 X」「被克 Y」（玩家同日要「显示对方对我方的克制」，选了两个方向都写）。被克等级 = `Suggestion.countered_grade`，就是克制等级取反（数据里 A 克 B 和 B 克 A 正好相反，克 S 必然被克 F）；两块都按对我好不好上色（S/A 绿、B/C 灰、D/F 红，被克那块用克制等级的颜色），收起后的小头像也有，悬停写合计和算法（`advisor.grade_view` 的 `by` / `by_note`、`web/view.js` 的 `gradeBadge`）；文字版写「克A 被克C」。还没有已选敌人时不显示。

**配合权重**：`docs/research/syn-weight/scripts/syn_weight.py`，3000 场样本外（统计截止点之后的新对局）同一批配对比较：0.5 比 1.0 区分度 +0.0018（95% 区间 −0.0004 ~ +0.0041）、阵容准确率 58.47% vs 58.03%、对数损失 −0.0010（−0.0023 ~ +0.0003）。三项方向都略好，都没出噪声。
第 45 节逐项相加拟合配合系数 0.75（区间含 1），和这个方向一致。按玩家要求改 `W_SYN = 0.5`。卡片上每个队友那一格的配合数仍是原值，「配合」合计那一步是减半后的（10-30 玩家要的「克制 2.1 和配合 2.1 等价」不再成立）。

**验证**：`test_engine.test_counter_grade`（分档、4 个各 +1 合计 ÷ √4 = 2 → S）、`test_familiar`（文字版、卡片 grade）；`DraftRateTest` 的整局式子改成乘 `W_SYN`。`suggest` 看了几组，等级和克制数一致。无头浏览器截图看过叠加层（卡片 / 小头像都有方块）。
行为快照：本机没有 `D:\dota-golden`，没跑（输出会因 W_SYN、等级、对线一行变化）。**没实战**。

## 74. 选人卡片加「对线」：候选英雄对上我这路对手好不好打（2026-11-09，`lanes.lane_edges` / `sources.stats.fetch_lanes`）

**起因**：同行 gg-go-next 有「对线模式」（STRATZ laneOutcome：赢线 / 输线 / 碾压）。我们的 `W_LANE`（按克制胜率给对线对手加权）回测没用，一直是 0；本局要点（`brief.py`）只在选好英雄后才看对线。玩家说「试试」。

**做法**：
- 数据：`update` 时拉 STRATZ laneOutcome，5 个位置 × 全部英雄（一次请求别名查 20 个，约 35 次请求），存 `data/lanes_r<min>-<max>.json`（`fetch_lanes` / `load_lanes`）。没 token / 没拉到就不显示。
- 指标：候选英雄打我这个位置，对上某个敌人「每 100 条线 赢线 − 输线」比它平时（对所有人）高多少，按 `LANE_K = 35` 条线收缩，少于 30 条不显示。收缩强度：单条线方差约 0.75，实查 ≥100 线的对位真实差别标准差约 15（中路约 25）→ 0.75 / 0.15² ≈ 33。好打 / 难打门槛 ±8（和本局要点 `brief.LANE_GAP` 一样）。
- 对谁：已选敌人里按猜的位置（和分路同一个猜法，玩家定的优先）会和我这路对线的（`lanes.lane_foes`，一号位对对面 3 / 4 号位）。
- **只显示、不进胜率**（`Suggestion.lane`，卡片「对位」下面一排「对线」，好打绿 / 难打红；文字版「对线 帕吉 -11 难打（xxx 线）」）。

**验证**：`test_lanes.LaneEdgeTest`（收缩、门槛、按猜的位置挑对手）、`AdvisorLaneTest`（卡片带对线、胜率不变、对面改打中路就不显示）。实拉一次数据：1 号位 127 个英雄。无头浏览器截图（一号位，敌 斧王 / 帕吉 / 莉娜）：幽鬼对帕吉 −11、冥魂大帝对斧王 −13 标红。
**没验证**：对线好打和这局赢不赢的关系没回测（对线结果本身第 28 节研究过能不能猜）；没实战。
