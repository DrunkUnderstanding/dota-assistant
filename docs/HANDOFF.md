# 开发交接文档

> 最后更新：2026-10-23。写给在游戏电脑上继续开发的人（包括 AI 助手）。使用说明见 [README](../README.md)。

## 1. 目标与范围

玩家原始需求：做一款**实时帮助玩 Dota 2** 的 AI 软件，包含 ① 英雄克制选取 ② 当局出装推荐 ③ 当前态势下的最佳打法；
**根据屏幕里的英雄阵容实时给建议**。

已确定的决定（来自和玩家的讨论）：

| 项 | 决定 |
|---|---|
| 用途 | 先自用 |
| 先做什么 | 选人推荐（①），出装和打法以后再说 |
| 模式 | 主要打**天梯全英雄选择** |
| 展示 | **叠加层 + 语音** 混合 |
| 项目 | 独立目录，与其他项目分开 |
| 玩家 | 好友代码（不公开，见本机 config.toml 的 account_id），超凡入圣 4 星，主打一号位，也打三 / 四号位 |
| 开发 / 游戏 | 开发在另一台电脑完成，**游戏电脑是另一台**（本文档就是为此写的） |

安全底线（不要越过）：只读屏幕截图 + Valve 官方 GSI；**不读游戏内存、不注入、不模拟键鼠输入、不显示玩家本来看不到的信息**。

### 2.1 回测结果（2026-10-21，`python -m dota_assistant backtest`）

样本：统计数据截止（match_id 9053619429）之后随机抽的 2555 场超凡～冠绝天梯全英雄选择，共 25550 手选人，
选人顺序和每人位置来自 STRATZ。每一手只用「轮到他时能看到的」信息重放。完整报告在 `data/backtest_report.txt`。

| 实际选的英雄在推荐里排第几 | 这手所在队伍胜率 |
|---|---|
| 第 1 | 58.1% ±4.2 |
| 第 2~3 | 55.3% ±2.5 |
| 第 4~10 | 53.1% ±1.4 |
| 第 11~20 | 50.4% ±1.2 |
| 第 21 以后 | 47.3% ±0.9 |

- 先选（第 1~4 手）：推荐前 3 胜率 56.3%，排 20 名以后 47.9%；后选（第 7~10 手）：54.9% vs 44.7%。
  区分度（排名与胜负的相关系数）先选 0.053、后选 0.075：后选更准，但先选也有用。
  **更正**：第一次回测（2449 场，另一批随机样本）先选那行是 52.5% vs 49.2%，当时据此说「早选几乎没用」，
  那是小样本噪声（推荐前 3 只有 453 手、区间 ±4.6），换一批样本就不成立了。
- 只看最终阵容预测胜负：英雄强度 56.8% → 加克制 57.8% → 加配合 57.9%。
- 样本里天辉胜率约 54.6%（地图偏向），阵容预测没建模这一项；选人推荐不受影响（同一手的候选都在同一边）。
- 这是相关不是因果：选得好的人可能也打得好，排名靠前组的胜率差里有一部分来自玩家水平。

**对线加权 / 早选防反制（`backtest --tune`，一半对局调参、一半验证）**：

| 改动 | 结果 |
|---|---|
| 对线对手克制权重 ×1.5 / ×2（`W_LANE` 0.5 / 1.0，敌方位置按其主位置推断） | 区分度略降（0.051 → 0.048~0.049），**没用** |
| 反制风险扣分（`W_RISK` 0.03~0.3，取最克我的 1 / 3 / 10 / 30 个未选英雄） | 变化 ±0.003，在噪声（约 ±0.01）以内，**没用** |

所以两项都默认关闭（常数保留在 `engine.py`，以后有新想法可以接着试）。保留了一个纯提示：
对面还剩 ≥3 手、且有未选英雄克我 ≥4 个百分点时，推荐理由里显示「易被反制：XX(+5.2%)」，不影响排名。

可能的原因（推测，未验证）：克制数据不分位置，单独放大对线对手只是放大噪声；
天梯里对面后手未必真会针对你（每个人优先选自己的位置和英雄），所以「可能被反制」平均下来影响很小。

## 3. 架构

```
            ┌────────────── update（每天一次，联网）───────────────┐
            │ OpenDota explorer → 克制 / 配合矩阵  data/stats_*.json │
            │ STRATZ heroStats → 英雄分位置胜率    data/positions_*  │
            │ STRATZ player   → 你每局的英雄 / 位置 data/player.json │
            │ Valve datafeed + CDN → 中文名 / 头像  data/heroes.json, data/portraits/ │
            └───────────────────────────────────────────────────────┘

run（实时）：
  live.Live 工作线程每 scan_interval 秒（网页操作 / 热键也排进同一个线程的队列）
    └ should_scan？（自动识别模式 + 已校准 + GSI 说在选人阶段 / 没 GSI 时勾了持续识别）
        └ capture.Screen.grab()（mss 截整屏）
          └ vision.recognize()：按 calibration.json 裁 10 个格子 → 和模板比相似度
            └ 连续两次结果一致才采用（躲开选人动画）→ 填进 Live.slots（控制面板的 10 个格子）
  格子（识别或手动）+ GSI（阵营、我选的英雄）
    └ advisor.Advisor.advise() → engine.Engine.suggest()
      ├ advisor.render_view() → 状态快照 → webui 本地服务 SSE → 叠加层 / 控制面板网页
      └ advisor.speech()：对面新选了谁 → Speaker.say()
  界面：webui 起 127.0.0.1 随机端口 → 启动 electron/ 外壳开两个窗口加载 web/ 下的页面
```

**控制面板的 10 个格子是唯一的「当前局面」**：识别和手动输入都只是往里写，推荐只从格子读。
这样纠正识别错误、手动兜底、学习模板都是同一个入口。

## 4. 模块地图

| `capture.py` | mss 截屏 |

| `gameplan.py` | AI 打法（本局要点第二页）：资料 = 本局数据 + 自己和对面五人的官方技能全文；每条带原文出处，程序核对出处；缓存 `data/plans/` |
| `llm.py` | 无头调用 Claude Code（订阅额度），选人盲测和 AI 打法共用 |
| `brief.py` | 本局要点：对线（laneOutcome）、起手装、强势期（按比赛时长的胜率）、对面要防、关键装备；`simulate()` 录像回放 |
| `coach.py` | 局内缺口提醒：`plan()` 开局定缺口，`Coach.tick()` 去重；`prepare()` 给实时版，`simulate()` 录像重放 |
| `demo.py` | 演示：按真实对局逐个选人，再当「假 Dota」把录像按 GSI 格式推给本地端口 |
| `speech.py` | 常驻 PowerShell 进程调 System.Speech，新句子打断旧句子 |
| `hotkeys.py` | RegisterHotKey 全局热键（不装键盘钩子） |
| `live.py` | 实时主控 `Live`（不依赖界面库）：局面格子、识别、推荐、语音、GSI、热键；状态整理成 JSON 快照 |
| `webui.py` | 本机 HTTP 服务（静态页面、头像、SSE 推快照、POST 操作）+ 启动 Electron |
| `web/` | 界面页面：`overlay.html` 叠加层、`panel.html` 控制面板、`view.js` 推荐卡片（两边共用）、`base.css` 配色 |
| `electron/` | 界面外壳：只开窗口（叠加层透明 / 置顶 / 穿透，控制面板普通窗口），无逻辑。`npm install` 装 Electron |
| `calibrate.py` | 校准窗口 |
| `kb.py` | 当前版本知识库：Valve 官方技能 / 天赋 / 物品原文、机制标签、玩家规则 |
| `knowledge/rules.toml` | 玩家确认过的经验规则（进 git） |
| `knowledge/mistakes.toml` | AI 常见误判：说错过、查原文纠正的说法（进 git，`kb mistake` 记录） |
| `backtest.py` | 样本外回测、调参 |
| `cli.py` | 所有命令入口 |
| `tests/` | `python -m unittest`：引擎、识别（合成截图）、GSI、播报文案 |

运行时生成、和机器相关的文件：`calibration.json`（校准）、`templates/`（学习模板，值得保留和拷走）、`shots/`（截图，不进 git）、`data/`（可重新拉，不进 git）。

## 5. 关键设计决策（为什么这么做）

1. **统计在 logit 空间相加 + 贝叶斯收缩**。克制收缩强度 `K_VS=400`、配合 `K_SYN=1100`，由「单局方差 / 真实效应方差」估出来（注释里有推导）。
   目的是不让小样本的极端胜率霸榜。个人胜率 `K_ME=40`，收缩很狠，因为混着队友影响。
2. **克制 / 配合数据自己聚合，不用现成接口**。OpenDota 的 `/heroes/{id}/matchups` 是职业比赛、样本只有几十局；
   改为用 explorer 直接对 `public_matches`（天梯全英雄选择 `game_mode=22, lobby_type=7`，时长 ≥15 分钟）做 SQL 聚合。
   explorer 单次查询会超时，所以按 `match_id` 分块（100 万一块，约 30 万局，6~9 秒），超时自动对半拆。
   时间窗口用 `IDS_PER_DAY = 155 万` 从最新 match_id 往回推（2026-10 实测值，以后可能漂移）。
3. **位置用 STRATZ**。公开对局没有位置信息，OpenDota 的定位标签太宽（斧王也挂 Carry）。STRATZ 有分段 × 位置的场次胜率，
   也能给出玩家每局的位置（约 28% 的局没解析，按英雄主位置 ≥60% 归类，否则不计）。没有 token 时退回标签粗筛 `fits_by_roles()`。
4. **识别用「校准 + 模板」而不是猜布局或上大模型**。开发时手上没有真实截图，不敢写死坐标；
   让玩家在自己的截图上框首尾两个格子、中间等距补齐，坐标存比例，同宽高比换分辨率不用重标。
   相似度是缩到 32×18、逐通道标准化后的余弦相似度，几毫秒一次。初始模板是官方头像，真实画面靠「学习模板」补。
5. **GSI 只用来知道阵营 / 阶段 / 我选的谁**。玩家身份下 GSI 拿不到敌方信息，这是 Valve 有意的限制，别想绕过。
6. **语音不用 Python TTS 库**。PySide6 的 QtTextToSpeech 在 Addons 包里，开发机装 Addons 撞了 Windows 长路径限制装不上；
   改成常驻 PowerShell + System.Speech，零依赖。
7. **热键用 RegisterHotKey**，不用 `keyboard` 之类的全局键盘钩子，降低被反作弊误判的可能。

## 6. 在游戏电脑上接手：检查清单

按顺序做，每一步都可能暴露开发机上测不到的问题：

- [ ] `pip install -r requirements.txt`，`python -m unittest` 全过
- [ ] 装 Node.js，`cd electron && npm install`；`python -m dota_assistant demo` 能弹出控制面板和叠加层（叠加层背景透明、鼠标点得穿、不进任务栏）
- [ ] `python -m dota_assistant say 测试` 有中文语音（没有就装中文语音包）
- [ ] `python -m dota_assistant update` 能跑完（网络环境不同，OpenDota / STRATZ 可能被墙或限速）
- [ ] `gsi-install` + 启动项 `-gamestateintegration`，`run` 起来后进游戏，控制面板状态栏显示「GSI：已连接」和正确阵营
- [ ] Dota 设成无边框窗口，`run` 后叠加层确实浮在游戏上方、鼠标能穿透；F7 / F8 / F9 / F10 生效；点叠加层右上角的锁解锁、真鼠标拖动、再点锁固定都正常，× 能关掉叠加层，固定时两个按钮以外的地方能点穿（第 14 节）
- [ ] **局内缺口提醒**（第 11.1 节）：打一局，开局有没有弹「开局提示」、死亡 / 每 5 分钟有没有弹卡片；
      F8 能关卡片；固定状态下鼠标移到「×」上能点关，其余地方照样点得穿；`gsi-dump` 看 `items` / `player` 的真实字段名
- [ ] **`gsi-dump` 打一局天梯的选人阶段**，看 `shots/gsi/*.json` 里 `draft` 有没有双方选择 / 禁用。有的话选人识别可以直接用 GSI、截图只当兜底（玩家 2026-10-22 问「选人时能用 GSI 吗」）
- [ ] **选人阶段 F10 截几张图**（禁用阶段、选到一半、选完、策略时间各一张，多攒几局）
- [ ] `calibrate` 框格子 → `recognize` 看相似度：
  - 认对的格子分数大概多少？空位分数大概多少？据此调 `match_threshold`
  - 如果认对的分数也很低（<0.6），说明官方头像和游戏内差别大，先用 `label` 教一轮再看
- [ ] 打几局，看叠加层位置是否挡视线（不合适就 F7 解锁拖开），语音时机是否合适

**截图里需要特别留意、开发时无法确认的事情**：
- 选人界面顶部英雄格的样子：是静态头像、动态立绘还是模型？选中前的空位长什么样？（影响识别方法是否要换）
- 禁用的英雄显示在哪、有几个格子、选人进行中位置会不会变
- 「我方 / 敌方」是否总是天辉在左（目前假设顶栏固定天辉左、夜魇右）
- 队友「预选 / 意向」的英雄是否也显示在格子里（会被当成已选）

如果顶栏格子在选人阶段根本不显示头像，就要换识别区域（比如选人界面中央的阵容展示），`Calibration` 结构不用改，重新框就行。

## 7. 下一步（建议顺序）

1. **真实截图验证识别**（第 6 节），按结果调整：阈值、要不要加「最高分和第二高分要拉开差距」的判据、特征尺寸。
2. **禁用识别**：目前禁用格可选校准，结果并入推荐排除列表，但没验证；全英雄选择的禁用是「提名 + 50% 生效」，要确认屏幕上显示的是哪种。
3. **队友预选**：如果能识别队友意向英雄，可以避免推荐撞车。
4. ~~**策略时间提示**（原 M4）~~：已做成「本局要点」卡片（第 15 节），先不念。
5. **出装推荐**（玩家需求②）：GSI 能拿到自己的物品和金钱；敌方阵容已经有了。先做「对面有 X 类英雄 → 优先 Y 类装备」的规则 + STRATZ 物品胜率。
   - **建在知识库上**（第 9 节）：「对面有什么」用敌方英雄的机制标签判断（提供闪避、施加破坏、沉默……），
     「我需不需要」先查自己英雄的标签（自带克敌机先 → 降低无视闪避类装备），再查 `knowledge/rules.toml`。
   - 规则要考虑**英雄自身技能对克制装的替代**。玩家纠正（2026-10-21）：卓尔游侠的大招被动已经能应对闪避，
     金箍棒对小黑是低优先级，不要因为对面有一个风行者就推金箍棒。同类情况（自带破闪避 / 自带驱散等）都应先查英雄自身能力再推克制装。
   - 2026-10-21 的复盘结论可作为规则雏形：射程 / 保命装（魔龙枪、飓风长戟）和黑皇杖的时间点比单件克制装更重要；
     对面控制或突进英雄多时，黑皇杖、飓风长戟前移。STRATZ `itemFullPurchase` 只返回最常见的前中期装备，后期装需另找数据源。
6. **局内打法**（需求③）：最难，建议做成事件提醒（肉山时间、对面核心没 BKB 等），不做持续解说。
7. 可选：大模型生成一句话解释（推荐理由目前是模板拼的，已经够用）。

## 8. 已知问题与风险

- `IDS_PER_DAY` 是写死的估计值；如果天梯量变化，「最近 14 天」会偏差几天，影响不大。
- STRATZ token 写在 `config.toml`，有效期到 **2027-10**；过期后到 stratz.com/api 重新领。token 曾在聊天里出现过，介意就重新生成。
- OpenDota 免费额度：每分钟 60 次左右，`update` 用约 60 次 explorer 查询，正常够用；429 会自动退避重试。
- 克制 / 配合数据不分位置（公开对局没有位置），分位置只修正了英雄自身强度。
- 叠加层在独占全屏下不可见，这是 Windows 的限制，只能用无边框窗口。
- 高 DPI：截图按物理像素、校准存比例，理论上不受缩放影响；叠加层按逻辑像素放置。多屏 + 不同缩放没测过。
  `monitor` 编号对截屏（mss）和叠加层（Electron `screen.getAllDisplays()` 的顺序）各自解释，多屏时两边顺序可能不一致。
- Valve 对第三方叠加层的政策会变，定期留意；本项目只做建议、不读内存，风险较低但不是零。

## 9. 知识库（2026-10-21）

起因：玩家指出「卓尔游侠不需要为风行者出金箍棒」，因为射手天赋自带克敌机先，而 AI 凭记忆给了错误建议。
玩家要求 AI「根据 Dota 2 特化」。做法不是训练模型，而是**让判断只基于当前版本官方原文 + 玩家确认的规则**。

**数据**：Valve 官方 datafeed（`www.dota2.com/datafeed/herodata`、`itemdata`、`patchnoteslist`），和游戏内说明同源。
`update` 时检查版本号（`patchnoteslist` 最新一项），变了才重拉，约 550 个请求、1~2 分钟。存在 `data/kb/kb.json`。

**三层**：
1. 原文：技能说明（`%占位符%` 已换成各级数值）、注释、神杖 / 魔晶、天赋（数值从技能的 `bonuses` 和天赋自身取）、
   物品属性 / 价格 / 冷却。官方 `immunity` 字段给出「是否无视技能免疫」。
2. 机制标签：`kb.TAGS` 里按官方措辞的关键词 + 排除词抽取，每个标签附命中的原句方便核对。
   例如区分「施加破坏」（末日对敌人施加破坏效果）和「怕破坏」（破坏会使被动魔法抗性失效）。
   标签是关键词匹配，会有少量误判；**引用时带上原句**，别只看标签名。
3. 玩家规则：`knowledge/rules.toml`，每条带来源（玩家原话 / 实现假设）、日期、在官方数据里的依据。
4. 常见误判（2026-10-23 加，玩家提议）：`knowledge/mistakes.toml`，AI（打法页 / 开发助手）说错过、查原文纠正的说法，
   每条 = 错误说法 + 正确说法 + 谁说错的 + 原文依据 + 可选 `has_tag`。
   - `kb hero` / `kb item` 输出末尾显示「常见误判」，开发助手回答机制问题前会看到；
   - 打法页：本局十个英雄相关的误判跟着各自的原文放进资料，不针对英雄的单列一段，系统提示要求别再犯（只放提示词，不做事后过滤，玩家选的）；
   - `has_tag`：正确说法依赖的机制标签，`RealDataTest.test_mistakes_still_hold` 每次跑测试都核对，版本改了机制会报出来；记录时也会先核对，标签不存在就不记。
   - 第一条是开发助手自己的错：照搬文档里「司夜刺客没有破坏」没查原文（第 15.1 节的更正）。
   - 和玩家规则的区别：规则是「应该怎么判断」（经验），误判是「这个说法事实上不对」（机制）。

**命令**：`kb hero 小黑`、`kb item BKB`、`kb find 克敌机先`（正则搜全部技能和物品）、`kb update [--force]`；
`kb mistake` 列出全部误判，`kb mistake --wrong 错误说法 --right 正确说法 [--hero X] [--item Y] [--who 开发助手] [--evidence 原文] [--has-tag 标签]` 记一条（英雄 / 物品名自动换成正式名）。
物品支持常用简称（BKB、MKB、跳刀、大推推……，见 `kb.ITEM_ALIASES`）。

**给以后的 AI**：回答任何「某技能 / 物品能做什么、能不能克制 X」之前，先 `kb hero` / `kb item` / `kb find` 查原文，
回答里引用原句；查不到就说查不到，不要用记忆补，**文档里写的机制结论也要回原文核对**（司夜刺客那次就是信了文档）。
玩家纠正了某个判断，就写进 `knowledge/rules.toml`；是机制事实说错了，用 `kb mistake` 记进 `knowledge/mistakes.toml`。

已知问题：修补匠、娜迦海妖各有 1 个天赋数值取不到（显示 `?`）；少数标签误判（例如「召唤」会命中描述性用词），
以原句为准。

## 10. 大模型选人盲测（2026-10-21，`python -m dota_assistant backtest-ai`）

玩家提出的验证方法：取历史对局选人进行到一半（第 3~6 手、双方都已有英雄）的时刻，让 AI 推荐，再看推荐和实际胜负的关系。

**做法**：每场对局取一个时刻；候选 = 实际选的英雄 + 这个位置（分段出场占比 ≥10%）随机 11 个，打乱。
AI 用玩家的 Claude Code 订阅无头调用（`claude.exe -p --safe-mode --tools "" --json-schema …`，Opus 5.5），
只给位置、双方已选、禁用、候选；不给对局 id / 胜负 / 实际选择 / 工具。对局都在 2026-10，晚于模型训练截止。
统计引擎在同一批题、同一组候选上也排一次。结果累积在 `data/ai_backtest.jsonl`。

**Windows 坑**：经过 npm 的 `claude.cmd` 调用时，空参数（`--tools ""`）和多行参数会被 cmd.exe 弄丢，
导致系统提示 / JSON schema 失效、还加载了项目 CLAUDE.md。现在直接调 `node_modules/@anthropic-ai/claude-code/bin/claude.exe`。

**300 个时刻的试点结果**（折合 API 价约 $3.3，走订阅额度）：

| 排序方式 | 区分度（实际选的排名越前 ↔ 越赢） |
|---|---|
| AI（Opus 5.5） | +0.108 |
| 统计引擎 | +0.076 |
| 两者平均名次 | +0.097 |
| **只按「这个英雄在该分段打这个位置的出场占比」** | **+0.178** |

样本 300 的噪声约 ±0.11，**以上差别都不显著**。但拆开看很有信息量：
- AI 的排序和统计引擎几乎不相关（平均 0.01），和「位置出场占比」相关 0.63；引擎和位置胜率相关 0.77、和出场占比只有 0.06。
- 也就是说 AI 主要在按「这个英雄是不是这个位置的常规选择」排，而单靠这一项的区分度反而最高。
- 当时推测「选了不常打这个位置的英雄的队伍更容易输」，**已在大样本上否定**（2026-10-22）：
  - 同样的出题方式在 2555 个时刻上（换 8 组随机候选）：只按出场占比的区分度平均 0.040，统计引擎 0.048。
    300 题里的 0.178 是小样本噪声。
  - 把出场占比加进引擎打分（log / 线性、多档权重），一半调参一半验证：最多 +0.001，权重稍大就变差。**没有采用。**
- 所以试点里 AI 的 +0.108 也很可能有相当部分是噪声。要判断 AI 有没有真本事，只能跑大样本。

**下一步**：如需结论，跑全部约 2555 个时刻的 AI 盲测（折合 API 价约 $28，走订阅额度，可能碰到速率上限，
`backtest-ai --moments 2555` 会接着已有结果续跑）。样本 2555 时噪声约 ±0.04，AI 要比引擎高出 0.05 以上才算真有优势。

**全量结果（2026-10-22，2555 个时刻，折合 API 价约 $27 + 试点 $3.3，走订阅额度）**：

| 排序方式 | 区分度（噪声约 ±0.039） |
|---|---|
| AI（Opus 5.5，无资料、凭自身 Dota 理解） | +0.032 |
| 统计引擎 | +0.055 |
| 两者平均名次 | +0.055 |

| 实际选的英雄排在 | AI 排序下胜率 | 统计引擎排序下胜率 |
|---|---|---|
| 前 3 | 52.4% | 55.2% |
| 第 4~8 | 51.9% | 49.1% |
| 第 9~12 | 46.5% | 49.1% |

**结论**：AI 没有比统计引擎更准（反而低 0.023，差距在噪声内，但方向不利）；把 AI 和引擎平均也没有提升。
试点的 +0.108 是小样本噪声。AI 与引擎的排序几乎不相关（0.00），说明 AI 的「Dota 常识」和真实对局统计是两回事。
**决定：选人排名不用大模型**，继续只用统计引擎。大模型留给「解释理由」「出装 / 局内建议」这类需要综合原文资料的场景，
而且必须喂知识库原文和统计数字，不让它凭记忆判断。

## 11. 局内缺口提醒（2026-10-22，`coach.py`，`python -m dota_assistant coach-sim <比赛编号...>`）

玩家需求（原话）：「AI 在战斗过程当中，有办法告诉我这把我缺少什么东西吗」；先修标签误判，再用模拟试。
**现状：模拟版完成（录像重放），实时版（接 GSI）未做。**

**先修了知识库标签**（`kb.py`）：
- 注释（notes）多是「能不能打到隐身单位」「被沉默时会不会打断」这类交互说明。现在能力类标签只看正文，
  只有 `NOTES_OK`（克敌机先、无视技能免疫、不可驱散、怕破坏、无视闪避）也看注释。「隐身」改成要求「进入 / 获得 / 变为…隐身」。
  修后「隐身」从 43 条降到 15 条，全是真隐身；露娜、灰烬之灵、沉默术士、帕吉不再被标隐身。
- 「沉默」不再被英雄名「沉默术士」误命中；「缴械」排除自身被缴械（钢背兽、獸）；「缠绕」排除给队友用的（寒冬飞龙极寒之拥）。

**判断逻辑**（全部数字对数字、原文对原文，不用大模型；阈值都是实现假设，在 `coach.py` 文件头）：
| 提醒 | 条件 |
|---|---|
| 黑皇杖 | 对面 ≥3 个英雄有控制（眩晕 / 沉默 / 缠绕 / 妖术 / 缴械）且自己英雄没有技能免疫；时间 = 同分段黑皇杖中位时间 +4 分钟，没有数据时 25 分钟。附「X 的 Y 无视技能免疫，黑皇杖挡不住」 |
| 金箍棒 / 血棘 | 对面有提供闪避的技能，且自己没有克敌机先、也没有玩家规则；小黑会改成开局提示「不用专门出」 |
| 反隐 | 对面有隐身技能 → 开局提示让辅助带粉；原文写「不会被反隐手段发现」的（斯拉克暗影之舞）注明粉没用 |
| 核心装晚了 | 同分段多数局会买、≥1500 金的装备，比中位购买时间晚 4 分钟还没有（合成后的也算有） |
| 节奏 | 10/15/20… 分钟正补低于同分段平均的 80%（否则看经济） |

提醒时机：死亡时 + 每 5 分钟；每次最多 2 条；同一条隔 6 分钟才重复，最多 2 次。
同分段数据来自 STRATZ `heroStats.stats(groupByTime)`（每分钟平均正补 / 经济）和 `itemFullPurchase`，缓存在 `data/bench/`。

**昨晚 6 局的模拟结果**（玩家 20:39~00:20，一号位）：
- 两局卓尔：20 分钟提醒魔龙枪（同分段一般 15 分钟，实际 21:16 / 26:05）；25 分钟提醒黑皇杖（实际 35:02 / 43:26）；
  原力法杖（实际 45:14 / 32:58）。开局都提示「射手天赋自带克敌机先，不用专门出金箍棒」。**两局 10 分钟正补（43 / 50）都不落后**。
- 敌法师（赢的那局）：10 分钟正补 30、15 分钟 60，落后同分段约 26~29%。
- 幻影长矛手：10 分钟正补落后 21%；对面 3 个控制但整局没黑皇杖。
- 斯温：黑皇杖 22 分钟就出了，没触发。

**更正**：之前出装复盘时说「同分段一号位 10 分钟通常 60~70 刀」，那是凭记忆说的，**是错的**。
STRATZ 实测超凡～冠绝卓尔一号位 10 分钟平均正补 43，敌法师 42。玩家两局卓尔 10 分钟正补（43 / 50）是平均水平，问题在装备节奏。

**已知局限**：
- 黑皇杖的同分段购买时间 STRATZ 不返回（`itemFullPurchase` 只给最常见的前中期装备），现在用 25 分钟兜底。
- 不知道敌方装备（GSI 玩家视角不给），所以不会说「对面出了 BKB」。
- 「有控制」只看有没有，不分强弱（风行者束缚击和谜团大招同等对待）。

### 11.1 实时版（2026-10-22）

玩家决定：**死亡时 + 每 5 分钟**检查；有缺口就在叠加层**弹卡片，可以关**；**先不念**（`config.toml` 的 `coach_voice = true` 能打开）。

数据流：Dota ──GSI──▶ `gsi.py`（`items` 订阅已打开，**要重新 `gsi-install`**）──▶ `Live.coach_tick()`（每秒一次，跟识别同一个循环）──▶ `Coach.tick()` ──▶ 叠加层卡片。
- **开局**（GSI 进入 PRE_GAME / GAME_IN_PROGRESS、换了 matchid）：后台线程 `coach.prepare()`，敌方阵容用选人时格子里的（识别 / 手填），
  自己的英雄用 GSI，位置用控制面板的。有开局提示（自带克敌机先、对面能隐身等）就先弹一张「开局提示」。

- **死亡**：看 `player.deaths` 计数涨没涨（不看 `hero.alive`，采样间隔长也不会漏）。**时间点**：`map.clock_time` 跨过 10/15/20…分钟。
- **卡片**：`kind=notice` + `closable`，黑皇杖那条用警示色。弹出时会取消「隐藏叠加层」；关法：F8（有卡片时 F8 先关卡片）、
  叠加层右上角「×」（固定状态下只有鼠标在「×」上时窗口接点击，其余穿透）、控制面板右侧预览里点「×」。比赛结束 / 回到选人自动收起。
  局内没卡片时叠加层不显示（和以前一样）。

**假 Dota 跑通（开发机，比赛 9054096051 卓尔，`demo --speed 60`）**：选完人后录像按 GSI 格式推到本地端口，叠加层依次弹出：
开局「风行者有闪避，但射手天赋自带克敌机先」→ 20 分钟魔龙枪 → 25 分钟黑皇杖（对面 5 个控制）→ 30:00 死亡时原力法杖 →
32:00 死亡时再提黑皇杖 → 比赛结束收起。和 `coach-sim` 的结果一致。加速时标题里的时间会比整点晚一点（每秒检查一次，1 秒 = 1 游戏分钟），真实速度下没这个问题。

**还没确认**（要在游戏电脑上 `gsi-dump` 看真实推送）：
- `player.net_worth` 有没有：没有的话节奏只比正补（`check()` 里经济那条不触发）。
- `items` 下的格子名是不是 `slot0~8` / `stash0~5`（目前按这个解析，`teleport0` / `neutral0` 不算）。
- 演示里装备用的是「到这一刻买过的全部东西」；真实 GSI 只给身上现有的，合成掉的零件靠 `item_tree()` 向上找，应该没问题。

## 12. 界面改版：网页 + Electron（2026-10-22）

玩家反馈（原话）：「看着不太美观」。看了 Overwolf 插件的做法后，玩家在两条路线里**选了 B**：
学 ow-electron 的做法，但用普通 Electron，做透明、置顶、鼠标穿透的窗口，界面用 HTML/CSS 写，Python 继续做识别和推荐。
另一条路线（保留 Qt，只改样式）没选。

**为什么不直接用 Overwolf / ow-electron**：Overwolf 的游戏内叠加层要把界面画进游戏画面，通常的说法是要注入游戏进程，
这违反第 1 节的安全底线；它的游戏事件还要 Overwolf 按应用单独开通。普通 Electron 窗口盖在「无边框窗口」模式的 Dota 上就够了，
不碰游戏进程。从 Overwolf 学的是**设计**：深色底配金色强调色、到处都有英雄头像、推荐做成卡片（头像、胜率、胜率条、理由标签）。

**结构**（见第 3、4 节）：`live.Live` 就是原来的 `ui.App` 去掉 Qt，逻辑逐条对应；`webui.py` 起本机服务；

## 14. 叠加层拖动 / 固定（2026-10-22）

玩家需求（原话）：「这个叠层应该允许我手动拖动位置，然后有一个固定按键可以固定位置，解锁固定以后又可以拖动」。

- 开关就在叠加层卡片右上角：一把锁（SVG 图标），关着 = 固定，打开（金底）= 可拖动；热键 `hotkey_lock`（默认 F7）同样切换。
  玩家第二次反馈（原话）：「这个叠层可拖动位置的按钮应该直接放在叠层上，这个为什么会放到主界面窗口当中，而且应该用一个锁和一个解开的锁来解释」，
  所以控制面板上的「解锁位置」按钮和解锁时的文字提示条都去掉了。解锁后叠加层强制显示（隐藏过也显示），卡片加金色虚线框。
- 固定状态下鼠标移到按钮（锁、×）上才接点击，其余地方照样穿透。
- 拖动：解锁后只有鼠标在卡片上时窗口才接鼠标，空白处照样穿透；
  按下后 Electron 主进程每 16ms 读系统光标位置移动窗口（不用页面坐标，免得高 DPI 换算出错），松开后把窗口高度重新拉到屏幕底部。
- 固定：再点一下锁或按 F7，恢复穿透（只剩按钮能点）。
- 位置和固定状态存在 `data/overlay.json`（占 `monitor` 那块屏的比例），优先于 `config.toml` 的 `overlay_x/y`；启动时会把位置收回屏幕内。
- 状态由 Python（`Live.overlay_locked`）统一管，快照里 `overlay.locked` 推给叠加层页面，页面再通过 `electron/preload.js` 告诉主进程。

**实现假设（非玩家原话）**：热键默认 F7（Dota 里如果占用了就改 `hotkey_lock`）；按住卡片任意处都能拖，不单设拖动把手；默认是固定状态。
**验证情况**：单元测试覆盖解锁 / 固定 / 位置保存和重启沿用。开发机实际起了 Electron（第一版，带文字提示条）：预加载脚本生效，
用 `SetCursorPos` 移动光标模拟拖动，窗口跟着移了 (-150, +80)，位置存回 Python。改成锁图标后同样在 Electron 里验证过，见下。
**没验证**：真手按住拖动（系统鼠标捕获 + hover 转发）、盖在 Dota 上时的表现，要在游戏电脑上试。

**关闭按钮**（2026-10-22，玩家原话：「这个叠层应该有一个关闭按钮，我可以随时关闭，当然快捷键也没问题」）：
- 叠加层右上角锁的右边加了 ×，和锁一样固定状态下也能点。动作 `close_overlay`：弹着局内提醒就只关提醒（和 F8 一致），
  否则 `user_hidden = True` 收起叠加层；解锁着点 × 会顺便固定（解锁状态会强制显示，不固定就关不掉）。
- 局内提醒卡片原来自带的 ×（`.ov-close`）在叠加层上隐藏，由右上角的 × 代替，避免两个 × 挨着；控制面板预览里照旧显示。
- 快捷键沿用 F8（`hotkey_toggle`），再按一次或点控制面板「显示叠加层」重新打开。
- **注意**：关闭后 `user_hidden` 一直保留，下一局选人也不会自动弹出来，要按 F8。玩家如果觉得不方便，可以改成新一局选人开始时自动恢复。
- 验证：单元测试 `test_close_button`；Electron 里点 × 后叠加层收起且按钮跟着隐藏，F8 重新打开；弹着提醒时 × 的提示变成「关闭这条提醒」，点了只关提醒（截图看过）。

**按钮点不到的 bug（2026-10-22 修）**：玩家反馈（原话）：「为什么我现在刚开的一个界面，这个叠层的锁定和关闭选中不了」。两个原因：
1. 启动时只写了 `setIgnoreMouseEvents(true)`（没有 forward），页面收不到鼠标移动，不知道鼠标到了按钮上；
2. 更根本的：靠页面 mouseover / mouseout 切穿透不可行——窗口一从穿透切到接鼠标，Chromium 立刻补发一次 mouseout，
   页面以为鼠标离开按钮又切回穿透，循环下去按钮永远点不到。之前用 CDP 调 `click()` 的测试绕过了鼠标，所以没发现。

**现在的做法**：页面报「可点区域」（固定时是锁和 × 的矩形，解锁时是整张卡片；`overlay:hit-rects`，布局变了才重报），
Electron 主进程每 30ms 读系统光标位置，在区域里就接鼠标、不在就穿透（状态变了才调 `setIgnoreMouseEvents`），完全不依赖页面鼠标事件。

**验证（真鼠标输入）**：测试脚本用 `mouse_event` 发真实的鼠标移动 / 按下 / 抬起（`SetCursorPos` 不经过系统鼠标输入，不算数；
脚本要先 `SetProcessDpiAwareness(2)`，否则 200% 缩放下坐标会错），并且先确认窗口已经不穿透才按下，避免点到下面的程序。
在开发机（4K 200%）上逐项通过：卡片外和固定时卡片中间都穿透；真点锁 → 解锁；真按住卡片拖动 → 窗口移动 (-100, +50) 并保存位置；
再点锁 → 固定，卡片中间恢复穿透；真点 × → 叠加层收起，原位置穿透；F8 打开后 × 又能点。**还差盖在 Dota 上实测。**

| 强势期 | `stats(groupByTime)`：打到第 t 分钟还没结束的局数 / 胜场 | 每个英雄在「30 分钟前 / 30~40 / 40 分钟后结束的局」里的胜率 - 自身总胜率，双方各取平均再相减；后期 - 前期 ≥ +1.5 说「越拖越强」，≤ -1.5 说「前期强后期弱」 |
| 对面要防 | `coach.plan()` | 同局内提醒；**辅助（4 / 5 号位）不再催你出黑皇杖 / 金箍棒**，改成「提醒核心」（局内提醒也一样） |
| 关键装备 | `coach.fetch_bench()` | 同分段核心装（≥40% 的局买、≥1500 金）的中位购买时间，最多 5 件 |

**强势期验证**（2555 场回测对局，超凡～冠绝，见第 2.1 节；曲线是 STRATZ 最近一周的数据，和这批对局时间有重叠，但每场只占每个英雄样本的万分之一左右）：
| 天辉阵容 | 30 分钟前结束的局天辉胜率 | 30~40 分钟 | 40 分钟后 |
|---|---|---|---|
| 越拖越强（1008 场） | 36.4%（151） | 48.0%（460） | 54.0%（372） |
| 前期强后期弱（967 场） | 76.0%（167） | 63.6%（396） | 42.4%（389） |
| 差不多（580 场） | 58.4%（89） | 56.4%（250） | 52.5%（219） |

### 15.1 AI 打法（2026-10-22，`gameplan.py`，`brief-sim <比赛编号> --ai`）

玩家需求（原话）：「在要点内看到前中后期我的打法，需要怎么做，干什么，如何打，面对劣势对线应该如何应对」。
统计数据给不出「怎么打」，所以这一页用大模型（`ai_model`，默认 Opus 5.5，走 Claude Code 订阅），按第 10 节的结论加约束：
- **只给资料**：本局要点全文（数字）+ 自己和对面五个英雄的 Valve 官方技能 / 天赋全文（标出对线对手）+ 队友机制摘要 + 玩家规则；
- **每条必须附 quote**：从资料里原样复制的一段话，`parse()` 去掉空白后核对必须出现在资料里，对不上的整条丢掉；
- 四段：对线期 / 中期 / 后期各 2 条，「对线劣势时」3 条，每条 ≤30 字，按位置写（核心 / 辅助）。

当时认为司夜刺客没有破坏；查知识库，司夜刺客的「复仇」原文写着「以攻击打破隐身…对目标施加破坏效果」，这条建议成立。

**以后可以做**（玩家已同意方向，未开始）：
