# 开发交接文档

> 最后更新：2026-10-21。写给在游戏电脑上继续开发的人（包括 AI 助手）。使用说明见 [README](../README.md)。

## 1. 目标与范围

玩家原始需求：做一款**实时帮助玩 Dota 2** 的 AI 软件，包含 ① 英雄克制选取 ② 当局出装推荐 ③ 当前态势下的最佳打法；
**根据屏幕里的英雄阵容实时给建议**。

已确定的决定（来自和玩家的讨论）：

| 项 | 决定 |
|---|---|
| 用途 | 先自用 |
| 先做什么 | 选人推荐（①），出装和打法以后再说 |
| 模式 | 主要打**天梯全英雄选择** |
| 展示 | **叠加层 + 语音** 混合 |
| 项目 | 独立目录，与其他项目分开 |
| 玩家 | 好友代码（不公开，见本机 config.toml 的 account_id），超凡入圣 4 星，主打一号位，也打三 / 四号位 |
| 开发 / 游戏 | 开发在另一台电脑完成，**游戏电脑是另一台**（本文档就是为此写的） |

安全底线（不要越过）：只读屏幕截图 + Valve 官方 GSI；**不读游戏内存、不注入、不模拟键鼠输入、不显示玩家本来看不到的信息**。

### 2.1 回测结果（2026-10-21，`python -m dota_assistant backtest`）

样本：统计数据截止（match_id 9053619429）之后随机抽的 2555 场超凡～冠绝天梯全英雄选择，共 25550 手选人，
选人顺序和每人位置来自 STRATZ。每一手只用「轮到他时能看到的」信息重放。完整报告在 `data/backtest_report.txt`。

| 实际选的英雄在推荐里排第几 | 这手所在队伍胜率 |
|---|---|
| 第 1 | 58.1% ±4.2 |
| 第 2~3 | 55.3% ±2.5 |
| 第 4~10 | 53.1% ±1.4 |
| 第 11~20 | 50.4% ±1.2 |
| 第 21 以后 | 47.3% ±0.9 |

- 先选（第 1~4 手）：推荐前 3 胜率 56.3%，排 20 名以后 47.9%；后选（第 7~10 手）：54.9% vs 44.7%。
  区分度（排名与胜负的相关系数）先选 0.053、后选 0.075：后选更准，但先选也有用。
  **更正**：第一次回测（2449 场，另一批随机样本）先选那行是 52.5% vs 49.2%，当时据此说「早选几乎没用」，
  那是小样本噪声（推荐前 3 只有 453 手、区间 ±4.6），换一批样本就不成立了。
- 只看最终阵容预测胜负：英雄强度 56.8% → 加克制 57.8% → 加配合 57.9%。
- 样本里天辉胜率约 54.6%（地图偏向），阵容预测没建模这一项；选人推荐不受影响（同一手的候选都在同一边）。
- 这是相关不是因果：选得好的人可能也打得好，排名靠前组的胜率差里有一部分来自玩家水平。

**对线加权 / 早选防反制（`backtest --tune`，一半对局调参、一半验证）**：

| 改动 | 结果 |
|---|---|
| 对线对手克制权重 ×1.5 / ×2（`W_LANE` 0.5 / 1.0，敌方位置按其主位置推断） | 区分度略降（0.051 → 0.048~0.049），**没用** |
| 反制风险扣分（`W_RISK` 0.03~0.3，取最克我的 1 / 3 / 10 / 30 个未选英雄） | 变化 ±0.003，在噪声（约 ±0.01）以内，**没用** |

所以两项都默认关闭（常数保留在 `engine.py`，以后有新想法可以接着试）。保留了一个纯提示：
对面还剩 ≥3 手、且有未选英雄克我 ≥4 个百分点时，推荐理由里显示「易被反制：XX(+5.2%)」，不影响排名。

可能的原因（推测，未验证）：克制数据不分位置，单独放大对线对手只是放大噪声；
天梯里对面后手未必真会针对你（每个人优先选自己的位置和英雄），所以「可能被反制」平均下来影响很小。

## 3. 架构

```
            ┌────────────── update（每天一次，联网）───────────────┐
            │ OpenDota explorer → 克制 / 配合矩阵  data/stats_*.json │
            │ STRATZ heroStats → 英雄分位置胜率    data/positions_*  │
            │ STRATZ player   → 你每局的英雄 / 位置 data/player.json │
            │ Valve datafeed + CDN → 中文名 / 头像  data/heroes.json, data/portraits/ │
            └───────────────────────────────────────────────────────┘

run（实时）：
  QTimer 每 scan_interval 秒
    └ should_scan？（自动识别模式 + 已校准 + GSI 说在选人阶段 / 没 GSI 时勾了持续识别）
        └ capture.Screen.grab()（mss 截整屏）
          └ vision.recognize()：按 calibration.json 裁 10 个格子 → 和模板比相似度
            └ 连续两次结果一致才采用（躲开选人动画）→ 填进控制面板 10 个格子
  格子（识别或手动）+ GSI（阵营、我选的英雄）
    └ advisor.Advisor.advise() → engine.Engine.suggest()
      ├ 叠加层 Overlay.show_lines()
      └ advisor.speech()：对面新选了谁 → Speaker.say()
```

**控制面板的 10 个格子是唯一的「当前局面」**：识别和手动输入都只是往里写，推荐只从格子读。
这样纠正识别错误、手动兜底、学习模板都是同一个入口。

## 5. 关键设计决策（为什么这么做）

1. **统计在 logit 空间相加 + 贝叶斯收缩**。克制收缩强度 `K_VS=400`、配合 `K_SYN=1100`，由「单局方差 / 真实效应方差」估出来（注释里有推导）。
   目的是不让小样本的极端胜率霸榜。个人胜率 `K_ME=40`，收缩很狠，因为混着队友影响。
2. **克制 / 配合数据自己聚合，不用现成接口**。OpenDota 的 `/heroes/{id}/matchups` 是职业比赛、样本只有几十局；
   改为用 explorer 直接对 `public_matches`（天梯全英雄选择 `game_mode=22, lobby_type=7`，时长 ≥15 分钟）做 SQL 聚合。
   explorer 单次查询会超时，所以按 `match_id` 分块（100 万一块，约 30 万局，6~9 秒），超时自动对半拆。
   时间窗口用 `IDS_PER_DAY = 155 万` 从最新 match_id 往回推（2026-10 实测值，以后可能漂移）。
3. **位置用 STRATZ**。公开对局没有位置信息，OpenDota 的定位标签太宽（斧王也挂 Carry）。STRATZ 有分段 × 位置的场次胜率，
   也能给出玩家每局的位置（约 28% 的局没解析，按英雄主位置 ≥60% 归类，否则不计）。没有 token 时退回标签粗筛 `fits_by_roles()`。
4. **识别用「校准 + 模板」而不是猜布局或上大模型**。开发时手上没有真实截图，不敢写死坐标；
   让玩家在自己的截图上框首尾两个格子、中间等距补齐，坐标存比例，同宽高比换分辨率不用重标。
   相似度是缩到 32×18、逐通道标准化后的余弦相似度，几毫秒一次。初始模板是官方头像，真实画面靠「学习模板」补。
5. **GSI 只用来知道阵营 / 阶段 / 我选的谁**。玩家身份下 GSI 拿不到敌方信息，这是 Valve 有意的限制，别想绕过。
6. **语音不用 Python TTS 库**。PySide6 的 QtTextToSpeech 在 Addons 包里，开发机装 Addons 撞了 Windows 长路径限制装不上；
   改成常驻 PowerShell + System.Speech，零依赖。
7. **热键用 RegisterHotKey**，不用 `keyboard` 之类的全局键盘钩子，降低被反作弊误判的可能。

## 6. 在游戏电脑上接手：检查清单

按顺序做，每一步都可能暴露开发机上测不到的问题：

- [ ] `pip install -r requirements.txt`，`python -m unittest` 全过
- [ ] `python -m dota_assistant say 测试` 有中文语音（没有就装中文语音包）
- [ ] `python -m dota_assistant update` 能跑完（网络环境不同，OpenDota / STRATZ 可能被墙或限速）
- [ ] `gsi-install` + 启动项 `-gamestateintegration`，`run` 起来后进游戏，控制面板状态栏显示「GSI：已连接」和正确阵营
- [ ] Dota 设成无边框窗口，`run` 后叠加层确实浮在游戏上方、鼠标能穿透；F8 / F9 / F10 生效
- [ ] **选人阶段 F10 截几张图**（禁用阶段、选到一半、选完、策略时间各一张，多攒几局）
- [ ] `calibrate` 框格子 → `recognize` 看相似度：
  - 认对的格子分数大概多少？空位分数大概多少？据此调 `match_threshold`
  - 如果认对的分数也很低（<0.6），说明官方头像和游戏内差别大，先用 `label` 教一轮再看
- [ ] 打几局，看叠加层位置是否挡视线（`overlay_x/y`），语音时机是否合适

**截图里需要特别留意、开发时无法确认的事情**：
- 选人界面顶部英雄格的样子：是静态头像、动态立绘还是模型？选中前的空位长什么样？（影响识别方法是否要换）
- 禁用的英雄显示在哪、有几个格子、选人进行中位置会不会变
- 「我方 / 敌方」是否总是天辉在左（目前假设顶栏固定天辉左、夜魇右）
- 队友「预选 / 意向」的英雄是否也显示在格子里（会被当成已选）

如果顶栏格子在选人阶段根本不显示头像，就要换识别区域（比如选人界面中央的阵容展示），`Calibration` 结构不用改，重新框就行。

## 7. 下一步（建议顺序）

1. **真实截图验证识别**（第 6 节），按结果调整：阈值、要不要加「最高分和第二高分要拉开差距」的判据、特征尺寸。
2. **禁用识别**：目前禁用格可选校准，结果并入推荐排除列表，但没验证；全英雄选择的禁用是「提名 + 50% 生效」，要确认屏幕上显示的是哪种。
3. **队友预选**：如果能识别队友意向英雄，可以避免推荐撞车。
4. **策略时间提示**（原 M4）：选完后念对线对手、起手装。STRATZ 有 `itemStartingPurchase` / `itemFullPurchase` / `laneOutcome`，按英雄 + 位置 + 段位查，接口都已验证可用。
5. **出装推荐**（玩家需求②）：GSI 能拿到自己的物品和金钱；敌方阵容已经有了。先做「对面有 X 类英雄 → 优先 Y 类装备」的规则 + STRATZ 物品胜率。
   - **建在知识库上**（第 9 节）：「对面有什么」用敌方英雄的机制标签判断（提供闪避、施加破坏、沉默……），
     「我需不需要」先查自己英雄的标签（自带克敌机先 → 降低无视闪避类装备），再查 `knowledge/rules.toml`。
   - 规则要考虑**英雄自身技能对克制装的替代**。玩家纠正（2026-10-21）：卓尔游侠的大招被动已经能应对闪避，
     金箍棒对小黑是低优先级，不要因为对面有一个风行者就推金箍棒。同类情况（自带破闪避 / 自带驱散等）都应先查英雄自身能力再推克制装。
   - 2026-10-21 的复盘结论可作为规则雏形：射程 / 保命装（魔龙枪、飓风长戟）和黑皇杖的时间点比单件克制装更重要；
     对面控制或突进英雄多时，黑皇杖、飓风长戟前移。STRATZ `itemFullPurchase` 只返回最常见的前中期装备，后期装需另找数据源。
6. **局内打法**（需求③）：最难，建议做成事件提醒（肉山时间、对面核心没 BKB 等），不做持续解说。
7. 可选：大模型生成一句话解释（推荐理由目前是模板拼的，已经够用）。

## 8. 已知问题与风险

- `IDS_PER_DAY` 是写死的估计值；如果天梯量变化，「最近 14 天」会偏差几天，影响不大。
- STRATZ token 写在 `config.toml`，有效期到 **2027-10**；过期后到 stratz.com/api 重新领。token 曾在聊天里出现过，介意就重新生成。
- OpenDota 免费额度：每分钟 60 次左右，`update` 用约 60 次 explorer 查询，正常够用；429 会自动退避重试。
- 克制 / 配合数据不分位置（公开对局没有位置），分位置只修正了英雄自身强度。
- 叠加层在独占全屏下不可见，这是 Windows 的限制，只能用无边框窗口。
- 高 DPI：截图按物理像素、校准存比例，理论上不受缩放影响；叠加层按逻辑像素放置。多屏 + 不同缩放没测过。
- Valve 对第三方叠加层的政策会变，定期留意；本项目只做建议、不读内存，风险较低但不是零。

调试 STRATZ 接口：POST `https://api.stratz.com/graphql`，头 `Authorization: Bearer <token>`、`User-Agent: STRATZ_API`（不带 UA 会被拒）。
可以用 `{ __type(name: "HeroStatsQuery") { fields { name } } }` 这类自省查询找字段。

## 9. 知识库（2026-10-21）

起因：玩家指出「卓尔游侠不需要为风行者出金箍棒」，因为射手天赋自带克敌机先，而 AI 凭记忆给了错误建议。
玩家要求 AI「根据 Dota 2 特化」。做法不是训练模型，而是**让判断只基于当前版本官方原文 + 玩家确认的规则**。

**数据**：Valve 官方 datafeed（`www.dota2.com/datafeed/herodata`、`itemdata`、`patchnoteslist`），和游戏内说明同源。
`update` 时检查版本号（`patchnoteslist` 最新一项），变了才重拉，约 550 个请求、1~2 分钟。存在 `data/kb/kb.json`。

**三层**：
1. 原文：技能说明（`%占位符%` 已换成各级数值）、注释、神杖 / 魔晶、天赋（数值从技能的 `bonuses` 和天赋自身取）、
   物品属性 / 价格 / 冷却。官方 `immunity` 字段给出「是否无视技能免疫」。
2. 机制标签：`kb.TAGS` 里按官方措辞的关键词 + 排除词抽取，每个标签附命中的原句方便核对。
   例如区分「施加破坏」（末日对敌人施加破坏效果）和「怕破坏」（破坏会使被动魔法抗性失效）。
   标签是关键词匹配，会有少量误判；**引用时带上原句**，别只看标签名。
3. 玩家规则：`knowledge/rules.toml`，每条带来源（玩家原话 / 实现假设）、日期、在官方数据里的依据。
